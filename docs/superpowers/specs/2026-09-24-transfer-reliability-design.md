# 传输可靠性与接收流程

## 目标

让两个传书实例之间的核心传输链路真正可用，增加明确的接收确认流程，并在不改变现有 React/Tauri/Rust 技术栈的前提下，完成影响最大的可靠性功能。

## 架构

第一个 QUIC 双向流负责完成双方设备认证。认证完成后，生成的 `PeerConnection` 保留在连接池中，后续所有控制流和数据流都复用该连接。传输请求、接受/拒绝响应、暂停、恢复和取消消息使用控制流。文件内容使用同一认证连接上的独立双向流，并以包含任务 ID 的数据开始消息开头，使服务端能够选择正确的接收任务。

后端在应用状态中保存待处理的接收请求。请求包含任务 ID、发送方身份、文件元数据和响应通道。后端发出 `transfer-request` 事件，前端显示确认弹窗，内容包括发送设备、文件数量、总大小和文件名摘要。接受/拒绝命令负责完成待处理请求。请求在 60 秒后过期；如果应用无法处理请求，则直接拒绝。

## 断点续传协议

接收端在写入文件内容前创建 `ResumeInfo`，并定期持久化分片位图和已传输字节数。收到数据开始消息后，接收端返回每个文件缺失的分片索引。发送端根据每个缺失分片的真实偏移量定位文件，只发送缺失分片。只有在任务 ID、文件 ID、文件大小、修改时间和校验和全部匹配时才允许续传；否则接收端清理旧状态并要求完整传输。

## 远端控制与历史记录

暂停、恢复和取消命令先更新本地任务，再通过现有认证连接发送给对端。双方都发出进度、完成和失败事件，并持久化终态历史记录。历史记录保存源文件路径、目标保存路径和文件元数据 JSON。打开位置操作使用保存的路径；重新发送操作使用保存的源文件路径，并在文件不存在时给出明确错误。

## 安全与验证

认证必须校验对端设备 ID 和证书指纹，不能继续使用当前的 mock 指纹。保留 UDP 端口 `45678` 和 QUIC 端口 `45679`。验证步骤包括 `pnpm build`、`cargo fmt --check`、`cargo check` 和 `cargo clippy --all-targets --all-features`，然后使用两台设备手动测试接受/拒绝、文件传输、暂停/恢复、取消、中断后续传以及历史记录操作。
